# Phase 2 — Persist Per-Run Error Details

**Status:** proposed (not yet implemented)
**Author:** Claude (lead session)
**Date:** 2026-05-03
**Triggered by:** Phase 1 audit (`.harness/diagnostics/phase1-partials-2026-05-03.md`) — partial-run rate too low (~5–7%) for `wrangler tail` to reliably capture
**Linked work:** F-009 amendment, T-009 extension, db/schema.sql migration

---

## 1. Goal

Make every partial or failed `sync_runs` row diagnosable from a single SQL query, without resorting to `wrangler tail` (which has 24-hour retention) or guesswork.

**Definition of done:** the moment a partial run lands in DB, a single query reveals which `error_code` fired (e.g. `tidal_429`, `tidal_404`) and which `spotify_id`(s) triggered it. From there, the Phase 3 fix is targeted and obvious.

## 2. Problem statement (recap)

The `sync_runs.errors` column is an `INT` count. The `sync_runs.error_code` column captures only the *terminal* failure reason (set by the outer catch, only when status='failed' with progress=0). Per-track failures inside `matchByIsrc` / `matchByFuzzy` are pushed into in-memory `errors[]` arrays and counted, but the per-track `error_code` and `spotify_id` are emitted only as `console.log` JSON and never persisted.

Concrete consequence: today's 5 partials all show `errors=1, error_code=null` — uninformative. We currently cannot tell whether they're `tidal_429`, `tidal_404`, `tidal_500`, or `tidal_parse_error` without a live `wrangler tail` window during the partial.

## 3. Design decision

### 3.1 Column shape

Add **one** new column to `sync_runs`:

```
error_details JSONB DEFAULT NULL
```

Stored as a JSON **array** of objects, each matching the per-track error record shape that `matchByIsrc` and `matchByFuzzy` already produce in memory:

```json
[
  { "spotify_id": "4hBKJTC82ubZ4wHieNy7aw", "error_code": "tidal_429", "message": "Second 429 received; track deferred to F-007" },
  { "spotify_id": "2Eu4XXTKnRQZM72w72Twmn", "error_code": "tidal_404", "message": "Tidal returned HTTP 404" }
]
```

### 3.2 Why array (not histogram)

Considered three shapes:

| Shape | Pros | Cons |
|---|---|---|
| Histogram `{tidal_429: 1}` | Compact, easy aggregate | Loses spotify_id — can't investigate which track |
| Array of objects | Zero transformation (matches in-memory shape), full forensic detail, histograms trivially computed via `jsonb_array_elements` | Slightly larger rows |
| Hybrid `{code: [spotify_id, ...]}` | Both views | Requires transformation, awkward for SQL |

**Chosen: array of objects.**

Rationale:
- Critical Phase 3 question is "which track is failing" not just "which code". `tidal_404` could mean a single Tidal-catalog gap (skip it) or a systemic ISRC normalisation bug (broader fix). We cannot distinguish without the spotify_id.
- The matchers already produce this exact shape (`PerTrackError[]`). Zero transformation cost.
- Row size impact: typical partial has 1–5 errors × ~150 bytes/entry = ≤1 KB. Negligible at our row count.
- Histogram is one SQL-level GROUP BY away when needed:
  ```sql
  SELECT detail->>'error_code' AS code, COUNT(*) AS n
  FROM sync_runs, jsonb_array_elements(error_details) AS detail
  WHERE status = 'partial' AND started_at > NOW() - INTERVAL '7 days'
  GROUP BY 1 ORDER BY 2 DESC;
  ```

### 3.3 Population rules

| Run outcome | `error_details` | `errors` | `error_code` |
|---|---|---|---|
| `succeeded` | `NULL` | 0 | `NULL` |
| `partial` (errors>0, progress>0) | non-empty array, length = `errors` | matches array length | `NULL` (terminal codes only) |
| `failed` (errors>0, progress=0) | non-empty array if matchers ran | matches array length | `NULL` (matchers caught) |
| `failed` (outer fatal, e.g. F-005 threw) | `NULL` | 0 | terminal code (e.g. `spotify_reauth_required`) |
| `failed` (wall-time exceeded) | array if matchers ran before cutoff, else `NULL` | matchers' total | `wall_time_exceeded` |

Invariant: `errors > 0 ⇒ error_details IS NOT NULL AND jsonb_array_length(error_details) = errors`

### 3.4 What we deliberately do NOT change

- No schema CHECK constraints (project ADR pattern: app-layer invariants)
- No new index on `error_details` — query path always starts with `status='partial'` filter (low cardinality, ~5%)
- No retroactive backfill — old rows stay `NULL`, queries treat NULL as "unknown details, see logs if still in retention"
- No change to `errors` INT column (kept for fast aggregate)
- No change to `error_code` TEXT column (kept for terminal codes; orthogonal concern)
- No change to logging — `console.log` JSON lines stay; this is additive DB persistence

## 6. Code changes (file by file)

### 6.1 `src/db/sync_runs.ts`

Type extension:
```ts
export type PerTrackError = {
  spotify_id: string;
  error_code: string;
  message: string;
};

export interface SyncRunUpdate {
  status?: SyncRunStatus;
  finished_at?: string;
  tracks_seen?: number;
  matched_isrc?: number;
  matched_fuzzy?: number;
  unmatched?: number;
  errors?: number;
  error_code?: string | null;
  error_details?: PerTrackError[] | null;   // <-- new
}
```

`updateRun()` SQL: extend the parameterized UPDATE to include `error_details = $N::jsonb` when the field is provided. Pass `JSON.stringify(value)` as the param. NULL when the field is null.

Schema-drift safeguard: the SQL string MUST contain the literal `error_details` token so the Stage 4 hook recognises the dependency on `db/schema.sql`.

## 10. Rollback plan

If a regression appears post-deploy:

**Code rollback:** `wrangler rollback` to the previous version. No schema rollback needed; the column is harmless if unwritten.

**Schema rollback (only if absolutely necessary):**
```sql
ALTER TABLE sync_runs DROP COLUMN error_details;
```
Safe because:
- No reads from this column outside the orchestrator
- No FKs reference it
- No code path depends on it for correctness; it's diagnostic-only

The CHECK on `status` is unchanged; orchestrator's status logic unchanged.

## 11. Risks & non-risks

### Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| Stage 4 hook fails on db/schema.sql sync mismatch | Medium | Apply Neon migration BEFORE adding `error_details` reference in code; add to schema.sql in the SAME commit as the code change. |
| `JSON.stringify` of a circular object throws | Very low | `PerTrackError` shape is plain `{string, string, string}`. No circular risk. Add a defensive try/catch in updateRun if anxious — but probably unnecessary. |
| Row size growth tips us over Neon's row limit | Negligible | Average partial has ≤5 errors × ≤200 bytes = ≤1 KB. Neon row limit is 1.6 MB. Three orders of magnitude headroom. |
| The diagnostic itself reveals a deeper issue (e.g., 50% of partials are `tidal_parse_error`) | Possible | This is the *desired* outcome — Phase 3 will be larger. Estimate Phase 3 effort once we have data. |

### Non-risks

- **Existing 503 tests breaking:** the change is purely additive in code paths. No existing assertion path changes. The only updateRun call signature change is an optional new field.
- **Production sync interruption:** zero. Schema migration is non-blocking (additive column). Code deploy is atomic at the Cloudflare layer.
- **Cost increase:** column adds ~1 KB to ~5% of rows = ~50 bytes per row average. Insignificant on Neon storage pricing.
- **Backfill ambiguity:** old rows with `error_details = NULL` mean "no DB-side data, see wrangler tail if within 24h retention". This is not a regression — it matches today's behaviour.
